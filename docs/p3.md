# Deterministic replay of WASI p3 components

component-ui and [proxy-component](https://github.com/chenyan2002/proxy-component) both record
a component's calls and replay them, but only for p2 components. A p3 component adds
`stream<T>`, `future<T>` and `error-context` values, async exports and imports, and with them
several calls and subtasks in flight at once. This file is the design for recording and
replaying such components deterministically, in both tools, and for exploring other orderings
of the same run. Nothing here is implemented yet; [Future work](#future-work-spikes) lists the
spikes that would test the design first.

It was written against jco 1.40.0 (jco-transpile 0.21.0), wasmtime 49.0.2, wit-bindgen 0.63.0,
proxy-component `128aa4e`, and the component model spec at
[`cd1ad0d`](https://github.com/WebAssembly/component-model/tree/cd1ad0dd7bb7773b79115ca10781c39fb0857024/design/mvp).
jco's async runtime is JavaScript embedded as strings in
`jco-transpile/vendor/js-component-bindgen-component.core.wasm`; it is cited by function name.

## Where nondeterminism comes from

Component model concurrency is cooperative: within one component instance only one thread runs
at a time, and it can only observe another thread, or the host, at well-defined points. The
spec lists what may be nondeterministic at those points (`Concurrency.md`, §Nondeterminism;
`canonical-abi/definitions.py`):

- Which waitable's event a `waitable-set.wait` or `poll` returns when several are pending
  (`WaitableSet.get_pending_event` shuffles).
- Which ready thread resumes (`Store.tick` picks at random).
- Whether a wait or yield with an event already pending blocks at all (`wait_until` flips a coin).
- The order of tasks released when backpressure is lifted, and which thread receives a cancellation.
- Everything the host does: when an import returns, and when and how much a host reads from or
  writes to a stream or future.

Calls between components, and streams and futures with wasm at both ends, are deterministic.

Neither runtime uses randomness for the internal choices:

| | jco 1.40 | wasmtime 49 |
|---|---|---|
| Which thread resumes | the oldest ready one, `ComponentAsyncState.tick` | the switch target, then the `high_priority` queue, then `low_priority`, `poll_until` (`src/runtime/component/concurrent.rs:1340-1375`) |
| Which pending event a wait returns | join order, `WaitableSet.getPendingEvent` | the lowest waitable first, `ready.pop_first()` (`concurrent.rs:2540`) |
| When the scheduler runs | `runTickLoop`, a `setTimeout` loop: 10 ms while idle, 0 after a resume | whenever host futures or work items are ready |
| Whether an async import call returns its result at once (RETURNED) or a subtask (STARTED) | a race: the import runs in a `queueMicrotask`, and its state is read after a `setTimeout(0)` (`_lowerImport`; its comment says engines order these differently) | fixed: `first_poll` (`concurrent.rs:3390-3427`) polls the host future once during the call |

So what varies between runs is **timing**: when host results arrive relative to what the guest
is doing. That is under the host's control, which is what the rest of this file uses.

## Values: streams, futures and error-context

Streams, futures and error-contexts are handles, like resources, but not of a named type. They
are written like resource handles, with a built-in name and a number:

- `#stream-1`, `#future-2`, `#error-context-3`. The element type comes from the WIT position,
  as `#x-1` is checked against its resource today.
- Only readable ends cross the boundary. The writable end stays with whoever created it, so one
  label names the stream.

What happens on a stream or future depends on which side writes:

- **Guest to host.** The guest writes, the host reads. The data is an *observation*, like an
  export's result: `#stream-1 -> b"hello\n"`, `#future-2 -> ok`. When the host reads, how much,
  and when it drops its end are host choices; the default is to read everything as it comes.
- **Host to guest.** The guest reads, and the host answers like an import:
  `#stream-3.read(4096) = b"line\n"`, `#stream-3.read(4096) = dropped`,
  `#future-4.read() = ok(5)`. The happy path is some data, then `dropped`.

An error-context is shown with its debug message.

## Trace format

A trace stays one sequence of lines, as answers files are today, and that sequence is the
schedule. What's new is that each line says which task it belongs to, and which line enabled it,
so that other valid orders can be derived from it.

```
> exports.run()                          // starts t1
t1: api.fetch("a") = started s1
t1: api.fetch("b") = started s2
s2 = "B"
s1 = "A"
//! t1 = "BA"
```

- Each `>` call starts a task, `t1`, `t2`, … in order. Calls the guest makes are prefixed with
  their task.
- An async import call either returns at once, `t1: api.fetch("a") = "A"` (RETURNED), or
  starts a subtask, `= started s1` (STARTED). The guest sees which, so it is recorded for every
  call.
- A subtask's result is a line of its own, `s1 = "A"`. These **host event** lines are what the
  host decides the timing of: subtask results, host stream reads and writes, future values,
  cancellations, and the start of export calls (`>`).
- A host event line is released when every line before it has happened and the guest is idle
  (see [the gate](#the-gate)). For a guest that never goes idle, e.g. one that yields in a loop,
  a line also gives the guest's scheduling point it was released at, e.g. `s2 = "B" @7` (see
  [the idle hook](#the-guest-side-idle-hook)).

Answers are matched per task: a task's calls have to come in the order its lines give, and each
call has to match its callee and arguments, as today. The order of lines across tasks is the
schedule. This replaces the rule that the whole file is one strict sequence; a p2 component has
one task at a time, so its answers files read as before.

### The partial order

A line can only happen after:

- the previous line of the same task;
- the line that started its subtask, for a subtask's result;
- the write it reads, for a stream or future read;
- the call that started the task, for the subtasks a task starts.

Any order of the lines that keeps these edges is a valid run of the same component: the host
could have produced it. Moving a host event line, e.g. `s1 = "A"` before `s2 = "B"`, gives
another run to try, and a tool can check the edges. A guest may behave differently in the new
order, since its tasks share memory; the lines past the first difference then become holes or
the happy path, per task.

### proxy-component's trace

proxy-component's `FuncCall` (`crates/trace/src/lib.rs`) would need a task id on each entry, a
status on `ImportRet` (`started` with a subtask id, or a result), and entries for subtask
results and for stream and future operations. It matches calls to returns by position today,
which only works for one call at a time.

## The gate

Holding back a host event is always legal: a host may complete an import, a stream copy or a
future at any later point, and the guest only sees a slower host. So a fixed order is enforced
by holding every host result, and releasing it when it's next:

1. Every host result is held when it arrives: an import's result, a stream chunk, a future's value.
2. When the guest is idle, the next result is released: the oldest on a first run, the next
   host event line on a replay. Then wait until the guest is idle again.
3. On a replay, if the guest is idle, the next line's event hasn't arrived and nothing else can
   make it arrive, the order is infeasible. This happens when a line is moved before what enables it.

### Why the first run is gated too

What a host sees is when a result arrives. What matters is when the guest receives it. They
differ. Say `run` starts `fetch("a")`, then `fetch("b")`, joins both subtasks to one waitable
set, and waits:

- `b` arrives at 3 ms and `a` at 5 ms.
- At jco's next tick, at 10 ms, both are pending. `getPendingEvent` takes them in join order,
  so the guest receives `a` first.
- A trace written from arrival order says `b`, then `a`. A replay that releases `b` first gets
  a different run.

With the gate, `b` is released alone, the guest takes it and goes idle, and only then is `a`
released. The order in the trace is the order the guest received them.

Recording which results were pending at each tick, as an unordered set, would also work, but it
needs to know when ticks happen, which neither runtime tells the host.

### RETURNED

Holding only ever makes a result later, so on its own the gate turns every async call into
STARTED. A replay answers at the call when the trace says the call returned at once. On a first
run, only an answer given at the call can be RETURNED: an answer from the answers file, or a
JavaScript import that returns a value. Whether the guest then gets RETURNED depends on the
runtime: always in wasmtime, and probably, but not certainly, in jco.

### What it doesn't cover

With one result released at a time, a guest never finds two results ready when it polls. That
case is legal, and some guests behave differently in it, but a gated run can't produce it.

## The guest-side idle hook

The gate needs to know when the guest is idle, and neither runtime says. jco's tick loop is
internal to its generated code, and wasmtime's `poll_until` just returns `Pending`. A timer is
the fallback: in jco, a quiet period longer than its 10 ms idle tick. It's slow, it guesses, and
it never fires for a guest that yields in a loop.

Every guest, whatever its language, blocks and yields through the same few canonical ABI
built-ins. In wit-bindgen 0.63, the executor's `callback` (`src/rt/async_support.rs:178-282`)
returns `CallbackCode::Wait` when nothing can make progress, and polls or returns
`CallbackCode::Yield` when a future woke itself. A stackful guest calls `[waitable-set-wait]`,
`[waitable-set-poll]` (`src/rt/async_support/waitable_set.rs:77-80`) and `[thread-yield]`.
Hooking these on the guest side gives:

- **Exact idleness.** Count the guest's tasks that can run: one more when an export starts, a
  callback is called or a wait returns; one fewer when a callback returns `Wait` or `Exit`, or
  a wait starts. Count the released results not yet delivered. The guest is idle when both are 0.
- **A clock.** The n-th wait, poll or yield is the same point in a replay as in the first run,
  so a release can be placed at a point, e.g. `@7`, where the guest is not idle.

The hook calls into whoever holds the results (the proxy, or component-ui's JavaScript) with a
synchronous call that doesn't block. A release from the hook is delivered as soon as the guest
waits, and nothing else runs in between, so it's deterministic. This works under any runtime,
for recording and for replay, without changing the runtime.

There are two ways to install it:

- **Patch wit-bindgen's runtime** to call the hook. Only for Rust guests, and they have to be
  rebuilt, but it's the quickest way to test the design.
- **Rewire the component.** The built-ins reach the guest's core module as imports, and the
  callback is named by `canon lift … (callback …)`. A wrapper core module between the built-ins
  and the guest's core instance can wrap them, and the callback, without changing the guest's
  code. The wrapper needs the guest's memory, for the event a wait writes; wit-component's
  fixup modules show how to bind it late. This keeps proxy-component's rule of instrumenting a
  component without changing its code.

## component-ui

jco is component-ui's runtime, so its built-ins are JavaScript that we can reach. In order of
preference, the idle hook can be:

1. **The rewired component**, with the hook as an import that component-ui's JavaScript answers.
   No patch to jco, and the same mechanism as proxy-component.
2. **A wrapper at instantiation**, for any component: jco's generated
   `instantiate(getCoreModule, imports, instantiateCore)` takes the function that instantiates
   each core module, so ours could wrap the core module's `[waitable-set-wait]`,
   `[waitable-set-poll]` and `[thread-yield]` imports and its callback exports. Under JSPI these
   may be `WebAssembly.Suspending` objects, or pass through `WebAssembly.promising`, which
   only takes wasm functions, so a JavaScript wrapper may not work.
3. **A patch of jco's output**, at its built-ins `waitableSetWait`, `waitableSetPoll` and
   `asyncYield`, and where `_driverLoop` handles the callback's result (`task.runCallbackFn`).
   They are named after the spec's built-ins, so they change less than the tick loop's internals.

The hook doesn't settle jco's RETURNED race in `_lowerImport`. If that turns out to be
unreliable, the ask for jco is an option to let the host decide the state an async import
returns, next to its existing `asyncDeterminism` setting.

Besides the scheduler, p3 needs these changes in component-ui:

- **Types.** bindgen stops at `todo!()` for streams and futures, and reads `error-context` as an
  `s32` ([`crates/bindgen/src/ast.rs:160-163`](../crates/bindgen/src/ast.rs) and `:183`).
  [`src/wit.ts`](../src/wit.ts) needs the types and their visitor methods.
- **Values and handles.** The labels above in [`src/wave.ts`](../src/wave.ts), tracking ends in
  [`src/resources.ts`](../src/resources.ts), and prompts for stream reads and future values in
  [`src/host-resources.ts`](../src/host-resources.ts) and [`src/dialog.ts`](../src/dialog.ts).
- **Loading.** WASI `@0.3` imports currently go to the p2 shim, as versions are stripped
  ([`src/loader.ts:19-28`](../src/loader.ts)), and every function is listed for jco's manual
  JSPI mode (`asyncMode`, `:44-52`), which async functions don't need. preview3-shim's browser
  build calls the preview2 shim's global modules, while component-ui makes a shim per instance
  with its own stdout, so its CLI part would need its own adapters.
- **One call at a time.** Several places assume a single call is in flight:
  - `CallActivity` ([`src/calls.ts`](../src/calls.ts)), which disables calls while one is pending;
  - `CallLog.pending()` ([`src/call-log.ts`](../src/call-log.ts)), which takes the last pending
    call as an import's parent;
  - the single cursor `Script.next` ([`src/answers.ts`](../src/answers.ts));
  - the single `Driver.stopped` callback ([`src/driver.ts`](../src/driver.ts));
  - `ResourceRegistry.settle` ([`src/resources.ts`](../src/resources.ts)), which blames the call
    that just finished for every handle that went away.

## proxy-component

proxy-component records in whatever host the component runs in, through a proxy composed with
`wac`, and replays `composed.wasm`, which has no imports, in plain wasmtime. For p3:

- **Replay is deterministic already.** Without a host there's nothing to time: only wasm calling
  wasm, which the spec makes deterministic, and wasmtime's fixed queues.
- **The proxy decides RETURNED or STARTED.** Its export for the guest's import calls
  `task.return` before blocking for RETURNED, or after for STARTED. The spec runs a wasm callee
  synchronously until it returns or blocks, so this doesn't depend on the runtime.
- **"Not your turn yet"** is a proxy task that waits, on a future inside the proxy, or by
  yielding, until a cursor in the proxy's memory reaches its line. All the proxy's tasks share
  that memory.
- **Recording** needs the idle hook: the proxy can't see the guest's waits, polls and yields,
  which go to the runtime, and the host runtime need not be wasmtime. Without the hook, the
  proxy could count the guest's calls into it, which is coarser; or yield and take its own
  resumption as a sign that the guest is idle, which depends on the runtime; or leave
  recording to the host with `--use-host-recorder`.

Today proxy-component's runner doesn't enable `wasm_component_model_async` (`src/run.rs`), its
bindings are generated without wit-bindgen's `async` feature, and `FuncCall` has no task ids.

## Phases

1. Stream, future and error-context types and labels in component-ui, with one call at a time.
2. Task-tagged answers files and the gate, in the CLI.
3. Several calls in flight, in the UI.
4. WASI 0.3, through adapters of our own or preview3-shim.
5. An async proxy, and the trace changes, in proxy-component.
6. Exploring orders: `--schedule random --seed N`, and enumerating the orders the partial order allows.

## Future work: spikes

The design rests on claims that small experiments could check first, on one shared fixture:
`p3-race`, a Rust component built with wit-bindgen 0.63's async support, whose
`run: async func() -> string` calls `fetch: async func(k: string) -> string` for `"a"` and
`"b"` and joins the results in the order they complete.

- **component-ui.**
  - Is jco deterministic when every answer is given at once? Run `run()` 100 times in one Node,
    and see whether the order and each call's RETURNED or STARTED vary.
  - With the gate and each working kind of hook: forcing `[b, a]` gives `"BA"`, and `[a, b]`
    gives `"AB"`, every time; releasing `a` before `fetch("a")` is reported as infeasible; and
    a run recorded with random host delays replays exactly.
- **proxy-component.**
  - A hand-written virtual host for `fetch`, composed with `wac` and run with
    `wasmtime run -W component-model-async=y`: forced orders give the expected results every
    time, and calling `task.return` before blocking gives RETURNED.
  - Recording: `p3-race` built with a patched wit-bindgen that calls the hook, a proxy that
    forwards to a host `fetch` with random delays, and replays that match their recordings.
- **Open questions.**
  - Whether jco's RETURNED race always comes out the same way within one engine.
  - Whether a wrapper at `instantiateCore` survives JSPI.
  - What rewiring a component needs from `wasm-encoder`'s component reencoding.
